# MON Inbound

Mobile web app (no build step, no framework) to plan and track truck unloading: the day before, someone enters the theoretical arrival time (ETA); the next day, the person at the dock opens the app, taps the truck, "Start Unloading", then "Finish Unloading" once done. Photos taken by MHE drivers are stored in Supabase.

Prototype built as an example for the ISD department — designed to be picked up and adapted freely.

Still **zero build, zero `package.json`, zero bundler**: `index.html` loads `js/main.js` with `<script type="module">`, and the browser resolves the `import`/`export` statements between files on its own — exactly like before, just split across several files instead of one. Netlify (or any static file host) serves this folder as-is, with no compilation step whatsoever.

Only external dependency: [SheetJS](https://sheetjs.com/) loaded from a CDN (cdnjs), used only by the "Import inbound plan" screen (see below) — the rest of the app depends on nothing external.

## Deploying the site on Netlify

1. Push this repo to GitHub (with all its `js/`, `css/`, `icons/` folders).
2. On Netlify: "Add new site" → "Import an existing project" → pick this GitHub repo.
3. Build command: leave blank. Publish directory: `/` (repo root, where `index.html` lives).
4. Deploy. Every future `git push` redeploys automatically.

## The four roles (Round 25: Admin MON IT and Nestlé added)

- **Admin MON**: protected by a 6-digit-minimum PIN code (default `748231`, changeable in the app via the ⚙ icon next to the role badge). Can enter/edit the ETA, start/finish/cancel/reopen the unloading, add/remove trucks, import the schedule, view Reporting, change the app's settings, change their own PIN.
- **Admin MON IT**: exactly the same rights as Admin MON (separate PIN code, default `913647`), **plus** a dedicated button to download the full photo archive (see "Archive photos" below) — the only thing this role has in addition.
- **Nestlé** (new, Round 25): the client who imports the trucks to be received themselves. Protected by a PIN code (default `205918`, changeable like the two roles above). Sees the list of trucks per day, the ETA, the photos (with download), and can import the schedule — but sees neither the damage/claim Remark nor the Reporting screen, and cannot edit the ETA, start/finish/cancel/reopen an unloading, delete a truck, add/remove a photo, or manually create a truck (the "+" button stays reserved for the two Admin roles).
- **MHE Driver**: no login. Sees the day's trucks, starts/finishes the unloading, adds photos. Can enter their name once (the "👤 Name" pill next to the role badge) — remembered on the device, not an account.

The role is chosen once per phone (stored locally on the device, no account) — the selection screen now offers the four buttons above instead of two. As before Round 25, all of this filtering remains purely a UI-side matter (no real server-side per-role security — see the security note in `supabase-schema.sql`): it's the same "honor system" logic as the single Admin PIN from Round 14, now extended to an external client (Nestlé), so keep that in mind if this ever becomes a sensitive point.

## Two data storage modes (auto-detected)

1. **Supabase connected** (recommended, see below) — every phone sees the same trucks and the same photos.
2. **Local (`localStorage`)** — fallback as long as Supabase isn't configured: data stays in that device's browser only. This is the active mode by default if `SUPABASE_URL`/`SUPABASE_ANON_KEY` are empty in `js/config.js` — handy for previewing the rendering while the Supabase project is being set up.

## Connecting Supabase

File involved: `supabase-schema.sql`.

1. Create an account / project at https://supabase.com if not already done.
2. In the project → **SQL Editor** → New query → paste the entire content of `supabase-schema.sql` → Run. This creates the two tables (`trucks`, `photos`), grants read/write access to the app's public key (see the security note at the top of the SQL file — this is a login-free prototype, so there's no real data-side security), and creates the `inbound-photos` storage bucket for photos.
3. In the project → **Settings** → **API**: copy the project's **URL** and the **anon public** key.
4. In `js/config.js`, right at the top of the file, fill in:
   ```js
   export const SUPABASE_URL = "https://xxxxxxxx.supabase.co";
   export const SUPABASE_ANON_KEY = "eyJ...";
   ```
5. Commit + push → Netlify redeploys automatically.

Once connected, adding a truck can be done directly from the app ("+" button, Admin role). To bulk-import the schedule (the manager's Excel file), see the next section.

### Importing the schedule (Excel/CSV) — Admin role

"📥" pill next to the role badge (Admin only) → "Import inbound plan". The manager picks their existing Excel file directly (e.g. "Incoming plan AMATA.xlsx") — nothing is sent anywhere before confirmation, everything is read in the browser ([SheetJS](https://sheetjs.com/) library, loaded from a CDN). All the logic for this feature lives in `js/importPlan.js`.

MON's actual file (`Incoming plan AMATA`) was used as the reference to build this parser; it handles its quirks:
- Column headers are in Thai/English and detected by keyword (not by position) — the header row itself is automatically located even when there are blank rows/titles above it.
- The "master log" sheets keep growing indefinitely (years of history in a single tab): a "from this date" filter (default today) discards the history to keep only upcoming trucks.
- Every sheet in the workbook is offered as a checkbox; by default, sheets whose name contains "incoming" (case-insensitive) are pre-checked, excluding the "รปภ" variant (a simplified security view, redundant with the full sheet) — so typically "RM PM incoming" + "Indirect incoming", not "MON+PALLET" (which is export data, out of scope for this app) nor "Master data".
- Duplicates (same PO + same date + same time + same carrier + same product/quantity/reference) already present in the app aren't re-imported — you can re-import the same updated file without duplicating trucks already created; a row added afterward to the file for an already-imported slot is correctly picked up as a new truck.
- **Several rows can share the same slot without being the same truck**: in the real file, it happens that a single delivery (same PO + same date + same time + same carrier) occupies several rows — a different line number ("รายการ"), with its own product/quantity, and often its own container number in the remark. Each row becomes **its own truck** (never merged with the others), with a "<PO> - Truck 1/2/..." marker to distinguish them easily on screen — see below.
- The material type (RM/PM, left-hand column) is preserved as a prefix in the "Product" field (e.g. "[RM] Poultry Meal…"); the Plant field is offered as an editable field on the import screen (default "AMATA", the site name in the reference file), remembered on the device from one import to the next — see "Multiple sites (Round 16)" below.

A preview screen shows the number of trucks ready to import before any write happens (with the "<PO> - Truck N" marker on rows sharing a slot) — nothing is created without clicking "Import".

**No column is lost**: in addition to the fields above (carrier, PO, quantity, product, date, time, remark), *all* columns from the source file are saved as-is in a `raw` column (JSON), including those without a dedicated field in the app (weighing, gross weight, punctuality, late penalties…). The schema update must have been run for this column to exist (see `supabase-schema.sql` — `alter table public.trucks add column if not exists raw jsonb;`, to run once if you had already run the script before). If it doesn't exist yet, the import still works (just without this safety net) and tells you so in the confirmation message. Once present, every imported truck shows a collapsible "All source file data" section in its detail sheet.

**Several trucks on the same slot, "RM PM incoming"/"Indirect incoming" sheets (Round 26, restored in Round 30 after a back-and-forth in Round 28)**: when several rows in the file share the same PO + date + time + carrier, each becomes **its own truck** — never merged. Those sharing a slot get a "<PO> - Truck 1/2/..." marker (`truck_label` column, see `supabase-schema.sql` — same update mechanism as `raw`), shown on the card, in the desktop table and in the detail sheet, with the product/quantity of that row underneath so they can be told apart at a glance; a truck that doesn't share its slot with anyone (the common case) shows nothing special and behaves exactly as before. Round 28 had briefly merged these rows into a single truck carrying several "lots" (`lots` column), on the strength of a confirmation from Khun Badeeson for one specific PO (4563895042) — but another PO (4563428496) showed that this is not a general rule for THESE sheets: two rows in the same slot can be two genuinely real and distinct trucks/containers, each with its own container number in the remark. As with `raw`, if the `truck_label` column doesn't exist yet on the Supabase side, the import still works: trucks are created separately, just without the "Truck N" marker, with a message flagging it.

**New "Call off" sheet for frozen goods, Round 31** (Khun Badeeson forwarded a new workbook, "2.CALL OFF FREOZEN 2026.xlsx", with its own "Call off" sheet — not to be confused with the weekly "Wk02_2026" etc. sheets in the same workbook, which remain out of scope): this sheet has nothing in common with "RM PM incoming" — English headers, no PO, no carrier name — so it has its own detection and parsing logic (`CALLOFF_FIELD_MATCHERS`/`importExtractCallOffRows()`/`importGroupCallOffRows()` in `js/importPlan.js`), triggered by the sheet name ("Call off", automatically pre-checked like an "incoming" sheet), not by its headers. Three deliberate differences from the "one truck per row" behavior above, chosen after inspecting the real file rather than on mere assumption:
- **A trip (Route + Trip + arrival date + time) becomes a single truck again**, with each row (a different lot number) as a lot of that truck (`lots` column, same mechanism as Round 28 for "RM PM incoming") — this time confirmed by the data itself: a single trip regularly carries several lots, sometimes several different products at once (e.g. chicken + salmon + tuna on the same trip), an unambiguous sign of a single truck with mixed loading, not several trucks that happen to share a time.
- **Only the "Mon > AM" direction (arrival at the plant) becomes a truck to track** — the return trip "AM > Mon" is ignored: the app tracks arrivals to be unloaded, not departures.
- **The carrier is fixed to "MON"** (internal shuttle, no external carrier named in the file) and the Plant field uses the same editable setting as the other imports (default "AMATA"). With no PO to display, every truck systematically carries a "<Route> - Trip <N>" marker (`truck_label` column, always populated here — not only when a slot is shared as with the other sheets) and an **"FZ"** badge (`trucks.mat_type`, two letters like RM/PM — Theo's call) next to the carrier. Shipped in Round 31 in neutral gray (the MON brand palette, Round 13, only reserved blue/orange/green/red, all already carrying a status meaning elsewhere in the app); in Round 32, Theo asked for a "glacial blue" for this badge — a dedicated teal/cyan (`--frozen`/`--frozen-soft`/`--frozen-ink`, `css/app.css`) rather than a shade of `--brand` (already RM's color, which would have made them hard to tell apart), with the same badge on the card and now also a row tint in the desktop table (`.matfz`, like `.matrm`/`.matpm`).

**Background file reading (`js/importWorker.js`)**: on a large "master log" file (years of history, several dozen MB), parsing the Excel workbook (`XLSX.read()` + sheet extraction) is pure computation that can take time — done on the main thread, it froze the page (no more scrolling, no more response to taps) for the whole duration. This parsing now runs in a Web Worker (`js/importWorker.js`, which loads the same SheetJS library from the same CDN): the page stays responsive (the "Reading…" banner animates normally) while the file is being read. If the Worker isn't available, or the CDN doesn't respond (blocked/slow network — the `import*Worker*` falls back after 6 seconds with no response), the import automatically falls back to the main thread exactly as before: this is a smoothness improvement, never a hard dependency — the import works in every case.

**Bug fixed (Round 18) — imported arrival times (ETA) shifted by ~6h43 on a phone/PC set to the Bangkok timezone**: discovered by comparing a real import against the source Excel file (07:00 in the file, "00:17" in the app; another truck 09:00 → "02:17" — the same 17-minute-56-second gap every time, never a random artifact). Cause: the import read the file with `cellDates:true`, which makes SheetJS build a real JS `Date` object for any date/time-formatted cell. A "time only" cell (Excel has no "time without date" type — it's encoded as a fraction of a day anchored to Excel's fictitious day zero, 12/30/1899) then becomes "December 30, 1899" built with the local JS constructor — and on a timezone set to Asia/Bangkok, the timezone database (ICU) resolves this historical date using Bangkok's pre-1920 mean local time (+06:42:04), not the modern +07:00. Reading this object back with UTC getters then recovers a time shifted by the gap between these two timezones (17 min 56 s) — invisible in the development sandbox (UTC timezone, where this historical quirk doesn't exist), so never detected before a real import on an actual phone/PC in Bangkok. **Fix**: reading is now done with `cellDates:false` (`js/importPlan.js` and `js/importWorker.js`) — the cell stays a plain number (the Excel serial number), converted by hand via pure arithmetic using `XLSX.SSF.parse_date_code()` (already used previously as a fallback, promoted here to the main path) — no `Date` object is ever constructed for these cells, so this timezone issue no longer arises at all. New regression test `tests/test_v2_import_time_serial.py`, which specifically forces the Asia/Bangkok timezone (the only way to make this bug reappear in a test) and checks that a raw Excel serial number (time) gives back the correct time. If trucks were already imported with shifted times before this fix, they need to be deleted and the same file re-imported (the new times will be correct) — see the Import section above for handling duplicates.

### Multiple sites (Round 16)

The import screen's "Plant" field is no longer hardcoded to "AMATA" in the code: it's now an editable text field (pre-filled with "AMATA" by default), remembered on the device (`localStorage`) from one import to the next — handy if MON Logistics one day imports another site's schedule from the same phone/tablet, without touching the code. No behavior change for single-site use: the default value stays "AMATA".

### Holding up over time (Round 16)

The day screens (Yesterday/Today/Tomorrow + the ◀/▶ arrows, see above) never show more than a ±`MAX_DAY_OFFSET`-day window around today. `loadFromSupabase()` (`js/api.js`) therefore no longer loads the entire `trucks` table on every refresh either: the query is bounded server-side to this same date window (`order_date=gte....&order_date=lte....`), so the amount of data transferred on every poll (~15s) stays small and constant, regardless of how much history has accumulated in Supabase over the months. The only two screens that legitimately need to look outside this window (import-time duplicate detection, and the Reporting screen below) each use their own explicit-range query (`sbFetchTrucksInRange`/`sbFetchTrucksForReport` in `js/api.js`) rather than depending on data already loaded on screen.

### Reporting screen (Round 16) — Admin role

New "📊" pill next to the role badge (Admin only), next to the ⚙ icon. It opens a summary screen over a chosen date range (default: the last 7 days): number of trucks, number completed, on-time rate (actual arrival compared to ETA, with the same `GRACE_MIN` tolerance as the cards' "late" status), average unloading duration (between "Start" and "Finish"), number of damage remarks recorded, and number of trucks with no recorded arrival (a data-entry quality indicator). All the logic lives in `js/reporting.js`; the query is independent of the day's display window (see above) and only loads the columns needed for the calculation.

**CSV export (Round 17)**: a "⬇️ Export CSV" button appears once the report is generated, below the KPI tiles (a solid button, not a plain text link — Theo missed it the first time, fixed right after the initial delivery). It downloads directly in the browser (no extra server round-trip — the same rows already used to compute the KPIs, already in memory) a `mon-inbound-report_<from>_<to>.csv` file with one line per truck (date, ETA, PO, carrier, status, actual arrival/departure times, damage remark), to work the numbers over in Excel rather than retyping everything from the screen. UTF-8 BOM at the start of the file so Excel opens it correctly. Any error during export (browser API refusing, etc.) now shows in a toast instead of silently doing nothing.

**PO and carrier in the export (Round 24)**: Theo, while testing the export, reported that the CSV didn't let you identify which truck each row came from without going back into the app. `po_no`/`carrier` were added to the columns (`sbFetchTrucksForReport()` in `js/api.js`, `exportReportCsv()` in `js/reporting.js`), right after `eta` — the full header is now `date,eta,po_no,carrier,truck_state,act_arrival,act_dept,damage_remark`. On the Supabase query side, the two columns are added at the **end** of the `select=...` clause rather than inserted between `eta` and `truck_state`, so as not to break the existing check in `tests/test_v2_reporting.py` on this query's prefix.

### Photos (test mode)

When Supabase is connected, a "Photos" section appears on every truck's detail sheet: an MHE driver (or the admin) can add up to 40 photos (`MAX_PHOTOS_PER_TRUCK` in `js/config.js` — a single place to change if this cap needs to move again; raised from 20 to 40 in Round 13, following feedback from Khun Badeeson who often takes many per shipment), at any time, in any order — this isn't tied to the Start/Finish buttons. Photos are resized/compressed in the browser (max 1280px, JPEG quality ~0.72, see `js/photoUtils.js`) before upload to stay lightweight over 4G, then stored in the Supabase `inbound-photos` bucket (public, direct read by URL) under `<truck id>/<PO or reference>-<timestamp>-<random>.jpg` — the folder stays the truck's UUID (guaranteed unique even if two trucks share the same PO number), only the file name reuses the PO to stay readable when browsing the bucket from the Supabase dashboard. Every photo keeps a record of who added it (the driver-supplied name, optional).

**Two separate buttons "📷 Take photo" / "🖼️ Gallery" (Round 19)**: until now, a single "+" button opened a `multiple` file picker (without the `capture` attribute, removed in Round 9 precisely to allow picking several existing photos at once). An on-site manager reported not being able to take a photo from an Android phone — confirmed to be genuine behavior on some Android devices/browsers: when `multiple` is present, the native picker often removes the "Camera" option from the menu (a single shot can't satisfy "pick several"), leaving only Gallery/Files. Fixed by splitting the two uses into two separate buttons/inputs: "📷 Take photo" forces the camera to open directly (`capture="environment"`, one shot at a time, guaranteed on every device); "🖼️ Gallery" keeps the existing `multiple` behavior for picking several already-taken photos. If fewer slots remain than photos selected from the gallery, the first ones are added and a message states how many were skipped (unchanged).

**"⬇️ Download photos" button (Round 20)**: once a truck has at least one photo, a button appears below the grid to download all its photos at once in a single `.zip` file (named after the PO, e.g. `PO-77701-photos.zip`), rather than opening/saving each photo one by one — requested by an on-site manager who compares it to a similar export ("FG export") she already uses elsewhere in MON's tools. Built entirely client-side (`js/photoDownload.js`) via the [JSZip](https://stuk.github.io/jszip/) library, loaded from a CDN only on demand (on the first click of this specific button, not when the app loads like SheetJS — most sessions never click it). If one or more photos can't be retrieved (a temporary network glitch), the zip still downloads with the ones that succeeded and a message states how many were skipped; if none can be retrieved, an error message shows instead of an empty zip.

**Photo names inside the zip (Round 24)**: Theo asked that once several zips from several trucks are downloaded side by side (a downloads folder, an email attachment), the photos be easier to sort/spot — date first, then scheduled time, then PO. Every photo inside the zip is renamed `<date>_<time>_<PO>-<NN>.<extension>` (e.g. `2026-09-10_09h00_PO-77701-01.jpg`) at the moment the zip is built (`zipEntryName()` in `js/photoDownload.js`) — the actual file name in the Supabase Storage bucket itself doesn't change at all, only the copy that ends up in the zip is renamed. **The zip itself now follows the same prefix** (`<date>_<time>_<PO>-photos.zip`, e.g. `2026-09-10_09h00_PO-77701-photos.zip`) — a first pass had left the zip's own name unchanged (just the PO, as before this round), assuming Theo only meant the contents; he reported (with a screenshot of his download history to back it up) that it was indeed the zip file's own name he wanted changed, fixed right after. **Each photo's index is zero-padded** (`-01`, `-02`... rather than `-1`, `-2`) — requested by Theo right after, so photos sort correctly in alphabetical order in a file explorer, and so it stays correct regardless of how many photos get added afterward (the zero-padding width automatically adapts to the truck's actual photo count, minimum 2 digits — so it stays correct even if the `MAX_PHOTOS_PER_TRUCK` cap, 40 today, is ever raised past 99). If a truck doesn't have an ETA yet (possible until it's marked "Completed"), the time becomes `no-time` rather than a broken name.

### Photo archive (Round 25) — Admin MON IT role

On Supabase's free tier (500 MB database, 1 GB file storage — see supabase.com/pricing), the photo bucket can fill up within a few weeks depending on truck/photo volume per day. Several options were considered with Theo (moving to Supabase's paid Pro tier; automatically deleting/archiving old photos after a delay; automatically moving them to MON's SharePoint via the Microsoft Graph API) — all rejected: the paid tier isn't wanted, and any automatic deletion/move carries a risk (a photo used as evidence for a supplier claim, deleted before anyone has used it). The solution chosen, simpler and risk-free: a **"⬇️ Download all photos (.zip)"** button, restricted to the **Admin MON IT** role, on the Reporting screen (📊) — it downloads all photos from all trucks in the chosen date range (the same "From"/"To" fields as Reporting) into a single `.zip` file, with a subfolder per truck inside the zip. **This button deletes absolutely nothing** — neither in the app nor in Supabase — cleaning up Supabase storage remains entirely a manual process, specific to MON's IT team, outside this app.

All the logic lives in `downloadPhotosArchive()` (`js/photoDownload.js`, reuses `loadJSZip()`/`dateTimePrefix()`/`zipEntryName()` already used by the per-truck download from Round 20/24), `runPhotoArchive()` (`js/reporting.js`, drives `ui.archiveBusy` and handles network failure), and `sbFetchTrucksForArchive()` (`js/api.js`, a dedicated Supabase query bounded to the chosen date range, with photos joined in — neither `loadFromSupabase()` nor `sbFetchTrucksForReport()` are suitable as-is, the former being bounded to the day's display window, the latter not loading photos at all). The downloaded file is named `archive_<from>_<to>.zip`.

## Other features

- **Installable on the home screen (PWA)**: `manifest.webmanifest` + the icons in `icons/` — on mobile, the browser offers "Add to Home Screen".
- **Vibration feedback**: a light vibration on tapping Start/Finish (`js/photoUtils.js`, `buzz()` function).
- **Retry on network failure**: if saving fails (network drop, etc.), a "Retry" button appears in the error message and replays the exact same action.
- **Protection against simultaneous double actions**: if two people act on the same truck at the same time (e.g. two drivers tap "Start" at the same time), the second action is rejected on the Supabase side (conditional update: "only update if the state hasn't changed in the meantime") and the app resynchronizes automatically rather than overwriting the state.
- **Refresh on returning to the app**: when the phone wakes up or you come back to the tab, data resynchronizes with Supabase automatically.
- **Smooth refreshing**: `render()` rebuilds all the HTML on every cycle (see below) — without care, this reset the scroll to the top of the page on every periodic refresh (~15s), giving an impression of a "violent jump" while reading the list. The scroll position is now preserved across every refresh. In addition, as long as a truck detail sheet is open (any role, any status — even a "completed" truck someone is just viewing), the periodic refresh is paused so as not to close an expanded section ("Lots on this truck", "All source file data") or interrupt reading; it resumes as soon as the sheet is closed.

- **Scheduled time always visible on the card**: once a truck is "late", the status pill shows the number of minutes late instead of the time — the scheduled time (ETA) therefore remains displayed separately on the card, so it's never lost from view even when very late.

## For the ISD team

The code is split by responsibility (see the repo structure above), with no framework — no build to maintain, just native ES modules that the browser loads directly:

- **`js/state.js`**: the two objects shared by the whole app — `state` (the trucks + the admin code, persisted) and `ui` (everything about the current screen, never persisted). All other modules import them and mutate them directly (`ui.tab = "today"`, etc.) — this is the only place that defines them.
- **`js/render.js`**: the `render()` function rebuilds all of the app's HTML on every state change and writes it into `#app` — no framework, no diffing.
- **`js/actions.js`**: every user-triggered mutation (ETA, start/finish/reopen, adding/deleting a truck, photos, PIN). Network calls go through `js/api.js`: `sbRest()` (`trucks`/`photos` table via Supabase's REST API, PostgREST) and `sbUploadPhoto()`/`sbDeletePhoto()` (Storage API) — no SDK to install.
- **`js/events.js`**: the single point where DOM clicks/keys/changes are listened to, routed by `data-*` attribute to the corresponding function in `actions.js` or `importPlan.js`.
- **`supabase-schema.sql`**: the two tables, their policies, and the storage bucket.
- The "New Truck" form in the app only covers the essential fields (carrier, plant, PO reference, date, ETA); more detailed fields (SKU, quantity, container…) can be filled in directly in Supabase (Table Editor) if needed, or the form can easily be extended in `addSheetHtml()` (`js/render.js`) / `createTruck()` (`js/actions.js`).
- Excel/CSV import: all in `js/importPlan.js`, functions prefixed `import*` (header detection `importFindHeaderRow()`, column mapping `importDetectColumnMap()`/`IMPORT_FIELD_MATCHERS`, extraction `importExtractRows()`). Column mapping is keyword-driven, not position-driven — to adapt it to another file format, just add label variants to `IMPORT_FIELD_MATCHERS`. The screen itself (`importSheetHtml()`) is in `js/render.js`. **Important (Round 18)**: `XLSX.read()` must always be called with `cellDates:false` (see `js/importPlan.js`/`js/importWorker.js`) — switching back to `cellDates:true` would reintroduce the time-shift bug on a Bangkok timezone (see the Import section above and `tests/test_v2_import_time_serial.py`). `importDateFromCell()`/`importTimeFromCell()` convert the Excel serial number by hand via `XLSX.SSF.parse_date_code()`, never via a `Date` object.
- Translations: everything is in `js/i18n.js` (`STRINGS` + `tr(key)`) — adding a key there is enough for it to be available everywhere else via `tr("myKey")`.
- **`js/photoDownload.js`** (Round 20): `downloadTruckPhotos()` loads JSZip from cdnjs on demand (first use only, never in `index.html`), fetches each photo (`fetch(p.url)`), adds them to the zip under their existing Storage file name, and triggers the download — same `Blob`/`URL.createObjectURL`/`<a download>` mechanism as `exportReportCsv()` (`js/reporting.js`, Round 17).
- **`js/offlineQueue.js`** (Round 16): offline action queue — JSON descriptors persisted in `localStorage`, replayed sequentially via the same `sbPatchTruckConditional()`/`sbCreateTruck()`/`sbDeleteTruck()` functions as live calls (`js/actions.js` passes a `queueDescriptor` to `runBackendCall()`), so all the existing conflict logic applies the same way on replay. `js/api.js` distinguishes a `fetch()` failure (a genuine network outage, `err.networkFailure = true`, queued) from an HTTP error response (server reachable but refusing, "Retry" behavior unchanged).
- **`js/reporting.js`** (Round 16, CSV export added in Round 17): Admin summary screen (📊), Supabase query over an explicit date range (`sbFetchTrucksForReport()` in `js/api.js`), calculations grouped in `computeReportStats()`, and `exportReportCsv()` which builds the CSV from `ui.reportRows` (the same rows used for the KPIs, kept in memory to avoid another query) and triggers the download via a disposable URL object. The whole function body is in a `try/catch`: an error (browser API, an extension blocking the download, etc.) shows in a toast (`reportExportFailed` in `js/i18n.js`) rather than doing nothing visible — this is what made it quick to rule out a JS bug when Theo first thought the export wasn't working (in reality the button, styled as a plain text link, was just not very visible — switched to a real `.btn.ghost` button with a ⬇️ icon right after).
- **`tests/`** (Round 16, completed in Round 17): Playwright suite (see the "Automated tests" section above) + `.github/workflows/test.yml` to run it in CI on every push/PR.
- **Search/filter/"coming soon" alert/undoable deletion (Round 17)**: `ui.searchQuery`/`ui.filterLateOnly` (`js/state.js`) filter the list in `listHtml()` (`js/render.js`), never the KPIs; `isDueSoon()` (`js/status.js`) is a function additive to `derive()`, never a replacement (no existing code that reads the derived status needs to know it exists); deletion now goes through `ui.pendingDeleteId`/`ui.pendingDeleteLabel` (`js/state.js`) for the duration of the undo delay, see `deleteTruck()`/`commitDelete()`/`undoDeleteTruck()` in `js/actions.js`.
- **The search field keeps focus across `render()` (Round 17)**: since `render()` rebuilds all of `#app` on every keystroke to filter the list live, a focused element would normally lose focus and cursor position on every character typed. `render()` (`js/render.js`) now captures the active element (id + selection) before rebuilding the HTML and restores it right after — same principle as scroll preservation (Round 11), applied here to any `<input>`/`<textarea>` that has an `id` and focus at render time.
- **Two separate photo buttons/inputs, never one (Round 19)**: `photoAddCameraInput` (`capture="environment"`, never `multiple`) and `photoAddGalleryInput` (`multiple`, never `capture`) in `js/render.js`, each routed to its own `data-photo-add-camera`/`data-photo-add-gallery` attribute in `js/events.js` — never merge the two back into a single input, that's exactly what broke taking photos on some Android devices (see the Photos section above). - **`js/settings.js` (Round 23)**: new module, deliberately separate from `config.js` — `config.js` stays the hardcoded default values (never changed at runtime), `settings.js` carries any **overrides** (`setSettingsOverrides()`/`getSettingsOverrides()`) and five functions `getGraceMin()`/`getMaxPhotosPerTruck()`/`getMaxDayOffset()`/`getDueSoonMin()`/`getUndoDeleteMs()` which return the override if it exists, otherwise fall back to the corresponding `config.js` constant. Everywhere else in the code (`status.js`, `actions.js`, `events.js`, `render.js`, `api.js`), the constant imported directly from `config.js` has been replaced with a call to the getter — none of these files know or need to know whether the value comes from an Admin setting or the factory default. The `SETTINGS_DEFS` array exported by this module drives the form (`settingsSheetHtml()` in `render.js`) and its validation/saving (`saveAppSettings()` in `actions.js`) all by itself — adding a 6th setting one day only requires a new entry in this array plus two `i18n.js` keys, nothing else to touch.
- **Loading shared settings (Round 23)**: `loadAppSettings()` (`js/api.js`) reads the single row of `app_settings` (id=1) and calls `setSettingsOverrides()` with its content; called once at startup (`js/main.js`) and on every cycle of the existing `setInterval`, alongside `loadFromSupabase()` — so a change made by an Admin on one device reaches every other device within one polling cycle (~15s), exactly like a truck change. Any network error/missing table is silently swallowed (a `.catch()` that does nothing): the app then keeps whatever overrides are already in memory (or the `config.js` defaults if none have ever been loaded), never a crash. **Pitfall avoided**: `defaultWindow()` (`js/api.js`, bounds the Supabase query to the Yesterday/Today/±N-days range) used to read the frozen `MAX_DAY_OFFSET` constant — if an Admin widens the day-navigation range from the new settings screen without this function following suit, the UI would let you navigate to a day whose data was never requested from Supabase (a day that would falsely appear empty). `defaultWindow()` now calls `getMaxDayOffset()` directly.
- **Full-screen photo viewer (Round 23)**: `ui.photoViewer` (`js/state.js`) is either `null` (closed), or `{ truckId, index, zoomed }`. `photoViewerHtml()` (`js/render.js`) looks up the up-to-date truck in `state.trucks` on every render (never a copy frozen at opening time), so it stays correct even if `state.trucks` changes in the meantime (periodic refresh). The admin delete button (`.photoslot-rm`) stays a **sibling**, never a child, of the open button (`.photoslot-view`, `data-view-photo`) in the DOM — a tap on one can therefore never also trigger the other, since `js/events.js`'s click delegation relies on `el.closest("[data-xxx]")`. Navigation `photoViewerStep(delta)` (`js/actions.js`) loops both ways (`((index+delta)%n+n)%n`) rather than stopping at the ends. **Bug found and fixed during this round**: the keyboard shortcut (Escape/←/→) was on `app.addEventListener("keydown", ...)` — tapping the image to zoom (an `<img>`, not focusable) moves focus to `<body>`, outside `#app`, and keys no longer reached this listener; fixed by listening on `window` instead (see the note in the Tests section above).
- **Admin settings screen (Round 23)**: `ui.settingsOpen`/`settingsError`/`settingsBusy` (`js/state.js`) drive the screen; `saveAppSettings()` (`js/actions.js`) reads each `<input id="setting-<key>">` by the name listed in `SETTINGS_DEFS`, validates that it's an integer within that entry's `min`/`max` bounds (otherwise shows `settingsErrRange` and leaves the screen open), converts it from displayed units to stored units via `divisor` (only `undoDeleteMs` differs: seconds on screen, milliseconds everywhere else), then either calls `setSettingsOverrides()` directly in fully local mode (no Supabase configured — a toast then specifies that the setting only applies to this device), or sends `sbSaveAppSettings()` (`js/api.js`, a `POST .../app_settings?on_conflict=id` with `Prefer: resolution=merge-duplicates,return=representation`) and only applies/closes after server confirmation. A failed save shows `ui.settingsError` (the message returned by Supabase, or `settingsSaveFailed` by default) and leaves the screen open rather than closing it silently.
- **Photo names inside the zip (Round 24)**: `dateTimePrefix(truckDate, truckEta)` (new, `js/photoDownload.js`) builds the `<date>_<time>` prefix shared by the zip itself (`<prefix>_<label>-photos.zip`) AND by each photo inside it (`zipEntryName()`: `<prefix>_<label>-<NN>.<extension>`, `extension` read by `extOf()` from each photo's existing `storagePath`, never modified) — `truckDate`/`truckEta` come from `js/events.js` (`dpTruck.date, dpTruck.eta`). The `NN` index is zero-padded (`String(index+1).padStart(width, "0")`) with `width = Math.max(2, String(totalCount).length)` — `totalCount` being the actual number of photos in THIS zip (`list.length`, passed by `downloadTruckPhotos()`), so the zero-padding width adjusts itself (minimum 2 digits) rather than being fixed at 2, in case `MAX_PHOTOS_PER_TRUCK` (`js/config.js`, 40 today) is ever raised past 99. The actual path in the Supabase Storage bucket (established in Round 9) isn't touched, only the two file names seen by whoever downloads. **First-pass pitfall**: the very first version only renamed the entries inside the zip, thinking that's what Theo meant by "have it take the date followed by the time followed by the PO" — he had to show a screenshot of his download history (still showing the old zip file name) to clarify that he meant the zip's own name. Worth keeping in mind for a similar request in the future: clarify whether "the downloaded file" means the container or its contents.
- **PO/carrier in the CSV (Round 24)**: `sbFetchTrucksForReport()` (`js/api.js`) adds `po_no,carrier` at the **end** of its `select=...` clause (never in the middle) — `tests/test_v2_reporting.py` checks this query's prefix by substring (`select=order_date,eta,truck_state`), so any future column to add to this report must follow the same rule: at the end of the list, never inserted before `truck_state`.
- **Three PIN roles + Nestlé role (Round 25)**: `state.adminCode` (a single value) became three fields — `adminMonCode`/`adminItCode`/`nestleCode` (`js/state.js`) — with an automatic migration: if a device already has an `adminCode` in memory (old seed/old local save) but not yet an `adminMonCode`, its value is carried over as-is into `adminMonCode` and then `adminCode` is removed, so that no already-configured device ends up locked out. `pinFieldForRole(role)` (`js/actions.js`) maps role → PIN field, used both by `submitPin()` (login, based on `ui.roleGateStep`: `"pin"`→Admin MON, `"pin_it"`→Admin MON IT, `"pin_nestle"`→Nestlé — unchanged for compatibility with existing devices/tests) and by `savePin()` (changing one's own PIN, based on `ui.role` this time). On the display side, `isAdmin()`/`isAdminIt()`/`isNestle()` (`js/render.js`) replace the old direct `ui.role === "admin"` checks scattered around this file — `isAdmin()` returns true for both Admin MON **and** Admin MON IT (the latter being a strict superset of the former), so everything that was already reserved for `"admin"` keeps working for both with no duplicated code; only `isAdminIt()` truly distinguishes the two (only for the archive button). Two calls made by judgment rather than explicitly requested by Theo, worth knowing about if future feedback questions them: the "+" button (manually creating a truck) stays reserved for the two Admin roles, never Nestlé (Theo only described its write capability as "upload the file", never manual creation); and Nestlé can change its own PIN like the two Admin roles (⚙ icon visible), so there's a way to rotate it without depending on an Admin role.
- **Top banner in two rows (Round 24)**: `render()` (`js/render.js`) now wraps the banner content in two `<div>`s (`.topbar-row1`, `.topbar-row2`) rather than a single horizontal flex — `.topbar-row1` carries `.brand-row` (logo) and a new `.idline` (role button + `.clockbox`); `.topbar-row2` carries `.rolebadgerow` (now only the settings icons + language toggle, plus the role button which has been moved up to row1) and `.syncrow`. `css/app.css` switches `.topbar` to `flex-direction:column`. Before implementing, `tests/test_v2_safe_area_top.py` was re-read in full to confirm it only checks `.topbar`/`.brand-word`'s bounding boxes (position, `padding-top`), never their nesting — the only test file that touches the banner's structure. All existing classes/ids/`data-*` attributes are kept identical (only their nesting changed), so click delegation in `js/events.js` needed no modification at all.
